### 1. 隐藏面板顶部的品牌图标

**改的是什么**：截图中菜单栏面板顶部居中的土星图标，代码上是 `Sources/Vorssaint/UI/MenuPanel/MenuPanelView.swift` 里 `MenuPanelHeader` 中的 `BrandMark(width: 48, tint: markTint)`（图片资源 `BrandMark.png`）。它出现在「常规面板」和「指标详情面板」两种布局中；灵动岛嵌入面板（`embeddedPanel`）本来就没有这个头部，不受影响。

**开关在哪**：设置 → 通用 → 外观 → 卡片底部的「在面板顶部显示品牌图标」。

**怎么实现的**：

| 文件 | 改动 |

| `Sources/Vorssaint/Core/Defaults.swift` | 新增 `DefaultsKey.panelShowBrandMark = "panelShowBrandMark"`；在 `registeredDefaults` 注册 `false`。注册后该偏好会随设置导出/备份（`SettingsBackupSupport.exportKeys()` 取自 `registeredDefaults`） |

| `Sources/Vorssaint/UI/Settings/GeneralSettings.swift` | `@AppStorage(DefaultsKey.panelShowBrandMark)` 默认 `false`，外观卡片底部加一个 `SettingsRow` + `Toggle` |
| `Sources/Vorssaint/UI/MenuPanel/MenuPanelView.swift` | `header` 改为 `@ViewBuilder`：仅当开关打开或 `AppInfo.isBeta` 时渲染 `MenuPanelHeader`；`MenuPanelHeader` 按 `showBrandMark` 条件渲染图标；`navigableChromeHeight` 改为按实际行高求和（详见下方「1a」），隐藏头部时不再预留空白 |

**边界**：Beta 版本的徽标和反馈按钮与图标共用同一个 header，因此 beta 构建里即使图标隐藏，header 仍会保留（只去掉图标），面板高度也按保留 header 计算。

#### 1a. 收紧面板上下留白（2026-11-06 追加）

隐藏图标后，面板顶部（原图标位置）和底部出现明显空白条：上游 `navigableChromeHeight` 的 180pt 基准含有预留量，固定 `.frame(height:)` 默认垂直居中会把多出来的高度均分到上下；再叠加 12pt 上下内边距，视觉上像一条空带。

| 改动 | 说明 |
|------|------|
| `navigableChromeHeight` | 不再用 180pt 减 48pt，改为按组件精确求和：`38`（标签栏）+ `34`（footer）+ `24`（两个 12pt 间距）+ `2 × panelVerticalInset`，再加 header `36 + 12`、更新横幅 `max(h,48) + 12`。SwiftUI 中 `EmptyView` 子视图不占间距（已实测） |
| `panelVerticalInset` | 隐藏 header 时上下各 11pt。实机小步迭代：上游 12pt（叠加旧高度误差）太空 → 6pt 太挤 → 9pt 仍偏小 → 11pt，接近左右 12pt 但不回到最初的松散观感；显示 header 时仍为上游的 12pt |
| `.frame(width:height:)` | 两个面板都改为 `alignment: .top`，避免任何残余预留高度被居中分配到顶部 |
| `metricChromeHeight` | 指标详情面板把 38pt 标签栏换成 24pt 返回/标题行，比常规面板少 14pt，单独计算，不再共用 |

用 SwiftUI `NSHostingView.fittingSize` 实测四种组合（有无 header × 有无横幅），新公式下「frame 高度 − 内容自然高度」均为 **0pt**，即不再预留空白。

**恢复上游行为**：把 `DefaultsKey.panelShowBrandMark` 的注册默认值改为 `true`，并把 `GeneralSettings.swift`、`MenuPanelView.swift` 中 `@AppStorage` 的初始值改为 `true`；或直接在设置里打开开关（用户侧，无需改代码）。

### 3. 定制构建彻底关闭应用自更新

**为什么**：默认构建的是官方同名 App（`com.vorssaint.utils`），而上游 `UpdateService` 把更新源写死为 `vorssaint/vorssaint-utils`。启动 6 秒后 / 每小时 / 面板打开时会自动检查；一旦上游发布新版本，用户点「更新」就会下载官方 DMG 并替换 `Bundle.main.bundlePath`，所有定制改动被静默覆盖。本地 `Info.plist` 与上游最新 release 同为 `3.4.3`，版本比较是严格 `>`，所以当时只是「已是最新」，上游一发新版就会触发。

**怎么实现的**（编译标志方案，A）：

| 文件 | 改动 |
|------|------|
| `build.sh` | 官方变体 `BUILD_VARIANT_FLAGS` 由空改为 `(-D VORSSAINT_CUSTOM_BUILD)`；`--dev` 仍只有 `-D VORSSAINT_DEVELOPMENT`，保留它的模拟更新 UI。测试 target 的编译命令不带这个标志，因此上游 `registeredDefaults` 契约测试不受影响 |
| `Sources/Vorssaint/Core/AppInfo.swift` | 新增 `isCustomBuild`（`#if VORSSAINT_CUSTOM_BUILD`）、`selfUpdateDisabled = isDeveloperBuild || isCustomBuild`、`defaultAutoCheckUpdates = !isCustomBuild` |
| `Sources/Vorssaint/Core/Defaults.swift` | `registeredDefaults[autoCheckUpdates]` 由字面 `true` 改为 `AppInfo.defaultAutoCheckUpdates`（定制构建为 `false`，测试 target 编译仍为 `true`） |
| `Sources/Vorssaint/Services/Update/UpdateService.swift` | `startAutomaticChecks` 直接返回（不建 timer、不联网、不弹横幅）；`autoCheckEnabled` getter 强制 `false`；`configureAutomaticChecks` 再加一道 `!isCustomBuild` 保护；`check(manual:)` 离线返回 `.upToDate`；`checkIfStale` 与 `downloadAndInstall` 用 `selfUpdateDisabled` 短路 |
| `Sources/Vorssaint/UI/Settings/SettingsView.swift` | 关于页的 `UpdatesView()` 在定制构建换成 `CustomBuildUpdateNotice()`，不再显示无效的开关与「立即检查 / 安装」按钮 |
| `Sources/Vorssaint/App/AppDelegate.swift` | `showUpdatePreview()` 在定制构建直接返回，彻底断掉安装预览入口 |
| `Sources/Vorssaint/Core/CustomBuildUpdateStrings.swift`、`Sources/Vorssaint/UI/Settings/CustomBuildUpdateNotice.swift` | **新增**。说明文案（简中 / 繁中中文，其余英文回退）与视图，延续不动上游 15 语言目录的做法 |

**保留的部分**：另一个「应用更新」功能（`AppUpdatesService`）本来就把自身和 `com.vorssaint` 前缀排除，不受影响；Developer 变体行为完全不变。

**恢复上游行为**：把 `build.sh` 官方变体的 `-D VORSSAINT_CUSTOM_BUILD` 去掉即可。所有新增判断都收在 `isCustomBuild` / `selfUpdateDisabled` 两个属性里，去掉标志后代码路径与上游一致（仅设置页与文案视图变成永远不显示的死代码，可一并删掉）。

### 5. 本地自签构建的风扇控制修复（2026-11-07 追加）

**症状**：本地 `build-and-run.sh` 构建的官方同名 App（自签证书 `Vorssaint Utils Signing`，无 Developer ID）里，风扇控制始终提示「受保护的风扇控制器不可用。请在登录项中允许 Vorssaint」——但登录项实际已允许（BTM 注册正常、守护进程能拉起）。

**根因**：官方同名构建不带 `VORSSAINT_DEVELOPMENT`，编译进 App 与守护进程的双向 XPC 校验规则是上游正式版的 `anchor apple generic and certificate leaf[subject.OU] = "3D485NHW29"`；自签证书永远不满足 `anchor apple generic`，于是两个方向都被拒，`FanControlService` 每次请求拿不到回复就报 `helperUnavailable`。上游没有这个问题（正式版真有 Developer ID），dev 变体也没问题（`VORSSAINT_DEVELOPMENT` 在运行时按自己的证书算规则）。

**怎么实现的**：

| 文件 | 改动 |
|------|------|
| `FanControlXPC.swift` | `import Security` / `import CryptoKit` 移出 `#if`；release 分支新增 `releaseCodeRequirement(identifier:)`：当前进程的 Team ID **不等于** 上游 `3D485NHW29` 时（自签 / 别的 Apple 证书签名），用运行时算出的叶子证书 SHA-1 生成 `identifier … and certificate leaf = H"…"` 规则；Team ID 相同（上游正式构建）或拿不到证书（ad-hoc，fail closed）时保持上游字符串原样。dev 分支逻辑未动，仅复用重构出的 `currentSigningInformation()` |
| `FanControlService.swift` | 新增 `staleRegistrationRecoveryIfNeeded()`：守护进程状态是 enabled、但 `fanControlHelperVersion` 从未存上值（= 从未握手成功过）、连续 3 次请求失败且本会话没试过时，自动「注销 → 重注册」并打开登录项设置；首次握手成功存上版本号后此路径永远不再进入。`requestStatus()` 失败路径计数并调用它 |

**边界**：换血只在「注册存在但从未握手」时触发，健康的安装（首次成功握手即写版本号）不会进入；注册后偏好被清空的极端场景会多一次登录项批准提示，属可接受的自愈代价。校验安全性不降：仍精确钉死到唯一一张证书，只是把「Apple 签发」换成「就是签这份构建的那张证书」。

**恢复上游行为**：`releaseCodeRequirement(identifier:)` 改回直接返回 `anchor apple generic and certificate leaf[subject.OU] = "\(teamID)" and identifier "\(identifier)"`；删除 `staleRegistrationRecoveryIfNeeded()` 及 `requestStatus` 中的计数与调用、`handshakeFailureCount` 属性。

## 三、风扇控制排障

下面两节记录风扇控制最容易误判成 bug 的两种状态，动手前先核对。

### 1. 卡在「受保护的风扇控制器不可用」（2026-11-22）

自签构建**重新签名安装后**可能遇到：面板提示「受保护的风扇控制器不可用。请在登录项中允许 Vorssaint，然后重试」，但登录项里看着没问题，重装 App 也不恢复。这不是代码回归，是 launchd / BTM 里残留了指向旧签名要求的 daemon 记录。

**怎么确认**（按顺序看，前一条命中即可定位）：

```zsh
# ① 守护进程跑不起来，launchd 明确报解析不到可执行文件
launchctl print system/com.vorssaint.utils.fan-control | /usr/bin/grep -E 'state|runs|exit|properties'
#    job state = spawn failed / last exit code = 78: EX_CONFIG
#    properties = ... | needs LWCR update | has LWCR
log show --predicate 'process == "launchd"' --last 10m --style compact | /usr/bin/grep -i fan-control
#    Could not find and/or execute program specified by service: 3: No such process: Contents/Library/LaunchServices/…
#    copy_bundle_path(...), error 0x6f - Invalid or missing Program/ProgramArguments

# ② 排除 bundle 本身的问题（目录结构、二进制、签名都正常才继续往下）
ls /Applications/Vorssaint.app/Contents/Library/LaunchServices/ /Applications/Vorssaint.app/Contents/Library/LaunchDaemons/
codesign -v -R="$(codesign -d -r- /Applications/Vorssaint.app/Contents/Library/LaunchServices/com.vorssaint.utils.fan-control 2>&1 | sed -n 's/^designated => //p')" \
  /Applications/Vorssaint.app/Contents/Library/LaunchServices/com.vorssaint.utils.fan-control
```

**怎么修**（不需要 sudo，走 App 自己的 `SMAppService.unregister()`）：

1. 设置 → 监视 → 风扇控制，把 **BETA 开关关掉**。这会触发 `syncWithPreferences()` → `restoreThenUnregister()` → `appService.unregister()`，清掉陈旧注册；确认 `defaults read com.vorssaint.utils fanControlHelperVersion` 变成空、`launchctl print` 查不到该 job。
2. 把 BETA 开关**重新打开**，打开菜单栏面板的风扇分区，点「允许风扇控制」，走一次干净的注册 → 登录项批准。
3. 验证：`launchctl print system/com.vorssaint.utils.fan-control` 应为 `state = running`、`runs = 1`、`last exit code = (never exited)`，且 `pgrep -f fan-control` 有进程；面板显示控制模式与风扇速度滑块即为握手成功。

**若上述无效**，再用 root 清理系统侧记录（副作用仅这一条）：

```zsh
sudo launchctl bootout system/com.vorssaint.utils.fan-control
```

**注意**：单纯重装 App（`build-and-run.sh`、`build.sh --install`）**不能**修复此状态 —— 实测重装后 `runs` 仍在增长（118 → 126），因为 BTM 记录不随 bundle 替换刷新。必须先让 App 注销再重新注册。

**相关遗留现象**：`fanControlHelperVersion` 可能残留一个既不是空串、也不等于当前 `VorssaintFanControlHelperVersion` 的值（本次实例是 `stale-needs-swap`，源码与脚本里都查不到该字符串）。它是判定「需要换血」的依据之一，遇到风扇控制异常时先 `defaults delete com.vorssaint.utils fanControlHelperVersion` 清掉再看。

### 2. 「调了没反应」的两个易误判点（2026-11-23）

排查调速不生效时，先排除下面两条 —— 两者都是上游既有设计，**不是缺陷**，改代码解决不了。

**① 滑块只「预备」，必须点按钮才「提交」**

手动调速是两步操作，顺序不能反，也不能省：

1. 拖「风扇速度」滑块到目标值
2. 点「启用手动控制」按钮

原因在 `FanControlSection.swift`：滑块的 binding 只写本地偏好，**没有任何 `onChange` 触发下发**——

```swift
private var coolingLevelBinding: Binding<Double> {
    Binding(get: { Double(selectedCoolingLevel) },
            set: { coolingLevel = Int($0.rounded()) })   // 只存，不发
}
```

真正下发的只有两处：`applyConfiguration(.manual(level: selectedCoolingLevel))`（点「启用手动控制」）和 `applyConfiguration(.curve(curves))`（点「应用曲线」）。所以「先点按钮再拖滑块」时，拖的那次不生效，需要再点一次。偏好值会持久化，但**不会自动下发**。

同一张卡片上还有个容易误读的对照：标题的「手动 · 100%」取的是 `snapshot.configuration`（**daemon 当前正在跑**的配置），滑块是**待提交**的值。二者不一致是正常的，不代表卡住。

**② 连接一断，正在跑的手动控制立刻作废**

daemon 的 `connectionClosed(_:)` 里有：

```swift
if self.owner == id, self.isCooling {
    _ = self.performRestore(reason: .appDisconnected)   // 立刻交还系统
}
```

只要 App 与 daemon 的 XPC 连接断开（关面板、App 退出、连接被回收），手动降温就会无声失效。所以验证调速效果时要**保持面板打开**观察转速。

怎么区分是「主动恢复」还是「被动断开」——看 daemon 日志最后一条的动因：

```zsh
log show --predicate 'process == "com.vorssaint.utils.fan-control"' --last 30m --style compact \
  | /usr/bin/grep -iE 'cooling session|restored'
# Cooling session started                        ← 点按钮后开始降温（成功）
# Automatic fan control restored: requested      ← 自己切回系统模式（正常）
# Automatic fan control restored: appDisconnected ← 连接断开被强制收回（要查为什么断）
```

**验证调速是否真的生效**：不要只看 UI，用目标转速反推 level。`coolingTargetRPM = min + (max - min) × level / 100`，例如 min≈1300、max≈6209 时 30% 应落在 **约 2773 RPM**；若目标仍是 5700+ 则是 90% 以上，说明提交没生效。

## 四、合并上游时的注意点

> 具体命令（添加 `upstream` remote、集成分支合并、源码包快照法、回滚、合并后锚点自检）见 [上游源码合并指南.md](上游源码合并指南.md)。本节只列**定制冲突面**，合并时逐项核对。

**会冲突的已有文件**（上游若改动同区域，需手工核对）：

1. `Sources/Vorssaint/Core/Defaults.swift` — `DefaultsKey` 面板分组、`registeredDefaults` 开头与 `autoCheckUpdates` 一行。
2. `Sources/Vorssaint/UI/Settings/GeneralSettings.swift` — `appearanceCard` 末尾、`@AppStorage` 声明区。
3. `Sources/Vorssaint/UI/MenuPanel/MenuPanelView.swift` — `header`、`MenuPanelHeader`、`showsHeader` / `panelVerticalInset` / `navigableChromeHeight` / `metricChromeHeight`、两个面板的 `.padding` 与 `.frame`。
4. `build.sh` — `BUILD_VARIANT_FLAGS` 的 `else` 分支（新增编译标志）。
5. `Sources/Vorssaint/Core/AppInfo.swift` — `isDeveloperBuild` 之后新增的三个属性。
6. `Sources/Vorssaint/Services/Update/UpdateService.swift` — `autoCheckEnabled`、`startAutomaticChecks`、`configureAutomaticChecks`、`check`、`checkIfStale`、`downloadAndInstall` 六处。
7. `Sources/Vorssaint/UI/Settings/SettingsView.swift` — `AboutSettings` 里 `UpdatesView()` 的调用处。
8. `Sources/Vorssaint/App/AppDelegate.swift` — `showUpdatePreview()` 开头。
9. `Sources/Vorssaint/Services/FanControl/FanControlService.swift` — `requestStatus()` 完成回调（失败计数 + 换血调用），以及 `staleRegistrationRecoveryIfNeeded()` 与 `handshakeFailureCount`。**2026-11-22 合并唯一冲突点**：上游把 `requestStatus` 改成 `finishRequest(generation, response:)` + `applyStatus(response)` 两段式，解冲突时保留上游的状态处理，只在 `guard let response` 失败分支里插入定制计数。
10. `Sources/Vorssaint/UI/Settings/SettingsDirectory.swift` + `build.sh` 的 `TEST_SOURCES` — `PanelBrandMarkStrings` 同时出现在两处：搜索索引里挂标题，测试源码列表里供覆盖测试解析。

> **风扇定制的编译标志**：`handshakeFailureCount` / `staleRegistrationRecoveryIfNeeded()` 的调用点包在 `#if VORSSAINT_CUSTOM_BUILD` 里。原因是上游 `Tests/generate_sources.py` 会把 `requestStatus()` 的**方法体原样**抽成测试 fixture，而测试 target 不带这个标志；不隔离就会编译失败（2026-11-22 实测）。

**纯新增、不冲突的文件**：`Sources/Vorssaint/Core/PanelBrandMarkStrings.swift`、`Sources/Vorssaint/Core/CustomBuildUpdateStrings.swift`、`Sources/Vorssaint/UI/Settings/CustomBuildUpdateNotice.swift`、`build-and-run.sh`、`docs/定制改动记录.md`、`docs/上游源码合并指南.md`。新增的 Swift 文件会被 `build.sh` 的 `Sources/Vorssaint/**/*.swift` 自动纳入编译，不需要逐个登记。

**上游会编译我们文件的测试**：`Tests/generate_sources.py` 从源码抽取方法体生成 fixture（`requestStatus`、`resume` 等都在列表里）。**改动这些方法时必须让定制代码可被编译标志隔离**，否则 `./build.sh --test` 会在 fixture 里报「no member」。

**上游新增的设置搜索覆盖测试**（2026-11-22 起）：`Tests/SettingsSearchCoverageTests.swift` 要求每个 `SettingsRow`/`SettingsCard` 的 `title:` 能回溯到**字符串类型上的属性**（`XxxStrings.localized(lang).title` 可以，`XxxStrings.title(lang)` 函数调用不行），且该引用必须出现在 `SettingsDirectory.searchItems` 里，否则报「shown in Settings but Settings search cannot find it」。新增设置项时照 `PanelBrandMarkStrings` 的写法即可。

**上游若重构了面板头部**：重点检查 `MenuPanelHeader` 是否还存在、`navigableChromeHeight` 里各行的高度常量（38 / 34 / 36 / 24 / 12）是否仍与实际布局一致；本定制已不再使用上游的 180pt 基准。
