# 上游源码合并指南

把上游 <https://github.com/vorssaint/vorssaint-utils> 的新代码合并进本仓库，同时完整保留本地定制改动。配套文档：[定制改动记录.md](定制改动记录.md)（记录「改了什么」），本文记录「怎么合并」。

- 创建日期：2026-11-06
- 适用仓库：`/Users/xmw/code/github/vorssaint-utils`
- 合并策略：**git merge**（不用 rebase），在集成分支验证通过后才推进 `main`

---

## 0. 最短流程（每次更新照这一段走）

前置：工作区干净、定制改动已提交、`upstream` remote 已配置（见第 2 节）。

```zsh
cd /Users/xmw/code/github/vorssaint-utils
git status --short                       # 必须为空（未跟踪的 IDE 目录除外）
git tag "fork-before-upstream-$(date +%Y%m%d)"
git fetch upstream main
git log --oneline HEAD..upstream/main     # 先看上游改了多少、改了什么
git checkout -b "sync/upstream-$(date +%Y%m%d)"
git merge --no-commit upstream/main       # 解冲突（见第 5 节）
./build.sh --test                        # 见第 6 节，连同锚点自检
./build-and-run.sh                       # 老夏本地实机验证
git commit -m "merge: sync upstream main as of $(date +%Y-%m-%d)"   # 验证通过后
git checkout main
git merge --ff-only "sync/upstream-$(date +%Y%m%d)"
git push origin main                     # 只有老夏明确指示才 push
```

合并完成后：**更新 `docs/定制改动记录.md` 顶部的「定制基线 commit」**，值取本次合并进来的上游 HEAD（`git rev-parse upstream/main`），并在修订记录追加一行（模板见第 10 节）。

| 本地分支 | `main`，跟踪 `origin/main`，非 shallow clone（完整历史）；本地领先 origin（按约定默认不 push） |
| 定制基线 | 每次合并后滚动更新，**以 `docs/定制改动记录.md` 顶部的「定制基线 commit」为准**。初始为 `26d3c9e1`（2026-11-05）；2026-11-28 时为 `0f0fdd91`（上游 v3.4.5 之后）。每次合并进来的上游 HEAD 都会成为下一次的天然 merge base |
| `upstream` remote | 已配置（第 2 节的一次性步骤已完成） |

上游 `main` 是受保护分支（要求 `Build & selftest`、`Swift 6.0.3 compatibility` 两项 CI）；这是上游自己的限制，fork 的 `main` 不受约束，本地用 `./build.sh --test` 代替验证即可。

### 1.2 合并前的硬性前提

1. **工作区必须干净**。首批定制改动（8 个修改文件 + 6 个新增文件）已由老夏实机验证后按 commit 纪律提交。以后每次合并前仍要确认 `git status --short` 对已跟踪文件为空：带着脏工作区执行 `git merge` 会被拒绝，或把未提交改动卷进合并结果。
2. **两个未跟踪目录不要提交**：`.openidea/`（IDE 生成）、`.workbuddy/`（项目记忆日志）。建议合并前加进 `.git/info/exclude`（本地生效、不改动仓库文件），命令见下方。
3. **先打 tag 再动手**（见第 0 节），这是唯一的轻量回滚锚点。
4. **不要用 `git pull --rebase` / `git push --force`**。fork 的 `main` 上有定制 commit 且已推到 `origin`，rebase 会重写这些 commit，之后只能强推才能同步，历史也会丢掉「哪次合并引入了哪个上游版本」的信息。

```zsh
printf '%s\n' '.openidea/' '.workbuddy/' >> .git/info/exclude
```

## 3. 路径 A：git 合并（推荐）

适用于能访问上游 git 仓库的常规情况。因为两边共享定制基线（最近一次合并进来的上游 commit，见定制改动记录.md 顶部）这个祖先，git 能做标准三方合并：**上游新增/修改的文件自动进来，本仓库的定制改动自动保留**，冲突只会集中在双方都改过的区域。

### 3.1 命令序列（带说明）

```zsh
# ① 锚点 + 取最新
git tag "fork-before-upstream-$(date +%Y%m%d)"
git fetch upstream main

# ② 合并前预览，判断风险量级
git log --oneline HEAD..upstream/main | wc -l            # 两点：上游新增的 commit
git diff --stat HEAD...upstream/main                     # 三点：上游相对 merge base 的改动，不含我们的定制
git diff --name-only HEAD...upstream/main | /usr/bin/grep -E 'build\.sh|MenuPanelView|UpdateService|Defaults\.swift|AppInfo\.swift|SettingsView|GeneralSettings|AppDelegate'
# 上面这个过滤列出与定制重叠的文件；命中越多，第 5 节的逐项核对越重要
#
# 注意 log 用两点（commit 集合）、diff 用三点（相对共同祖先的变更）。
# 如果 diff 写成两点，会把「上游缺少我们的定制」也算成变更，stat 虚高、误导判断。

# ③ 在集成分支上合并，不直接动 main
git checkout -b "sync/upstream-$(date +%Y%m%d)"
git merge --no-commit upstream/main

# ④ 若有冲突：按第 5 节逐个解决 → git add <file> → 第 6 节验证
git status --short

# ⑤ 验证通过后才提交，再快进 main
git commit -m "merge: sync upstream main as of $(date +%Y-%m-%d)"
git checkout main
git merge --ff-only "sync/upstream-$(date +%Y%m%d)"
```

`--no-commit` 让合并结果停在工作区，方便在提交前跑构建和自检；`--ff-only` 保证 `main` 只接受已经验证过的那个集成结果，不会意外产生分叉。

### 3.2 为什么不建议直接在 `main` 上合并

直接在 `main` 上 `git merge` 也能成功，但一旦冲突解错或编译不过，`main` 就已经前进了，回滚要 `reset`。集成分支的成本只是多两条命令，换来「验证不通过就整条丢掉」的干净边界。

## 4. 路径 B：只有源码包（zip / tarball）时

适用于上游仓库暂时无法 clone、只有 release 的 `Source code (zip)` 或某个 tag 归档的情况。**不要**把源码直接解压覆盖当前工作区 —— 那样定制改动会被静默抹掉，且 git 无法做三方合并。

### 4.1 原理

从共同基线（定制基线 commit，即最近一次合并进来的上游 commit，见定制改动记录.md 顶部）切出一个快照分支，把工作区整体替换成上游源码，提交成一个「上游快照」commit；再把这个分支 merge 回 `main`。这样 git 仍有正确的 merge base，能自动区分「上游变更」与「本仓库定制」。

### 4.2 命令序列（zsh / macOS 自带 openrsync）

```zsh
# ① 先准备干净工作区与上游源码目录（解压后的顶层目录）
SRC_DIR=/Users/xmw/Downloads/vorssaint-utils-main     # 改成实际路径
test -f "$SRC_DIR/build.sh" || { echo "路径不对"; exit 1 }

# ② 从基线切快照分支（基线 = 定制改动记录.md 顶部的「定制基线 commit」，
#    初始 26d3c9e1，之后每次合并滚动为新值；不能从 main 的最新定制 commit 切）
BASE=<定制基线 commit>            # 例：BASE=0f0fdd91eb80e509f737f2c4c1f8630b707f6537
git checkout -b "sync/snapshot-$(date +%Y%m%d)" "$BASE"

# ③ 排除项抽成数组，两条 rsync 共用，避免 dry-run 与真跑漏掉保护项
EXCLUDES=(
  --exclude '.git/'
  --exclude '.openidea/'
  --exclude '.workbuddy/'
  --exclude 'build/'
  --exclude '.DS_Store'
  --exclude 'AGENTS.md'
  --exclude 'CLAUDE.md'
  --exclude 'docs/定制改动记录.md'
  --exclude 'docs/上游源码合并指南.md'
  --exclude 'build-and-run.sh'
  --exclude 'Sources/Vorssaint/Core/PanelBrandMarkStrings.swift'
  --exclude 'Sources/Vorssaint/Core/CustomBuildUpdateStrings.swift'
  --exclude 'Sources/Vorssaint/UI/Settings/CustomBuildUpdateNotice.swift'
)

# ④ 先 dry-run 看清楚会删什么、加什么
/usr/bin/rsync -a --delete --dry-run -v "${EXCLUDES[@]}" "$SRC_DIR/" ./

# ⑤ 确认删除列表里没有误伤，再真跑（只去掉 --dry-run）
/usr/bin/rsync -a --delete -v "${EXCLUDES[@]}" "$SRC_DIR/" ./
git status --short                    # 审阅变更清单
git diff --name-status "$BASE" -- . | /usr/bin/grep '^D'   # 逐条确认删除项，误删见第 4.3 节
git add -A
git commit -m "chore: import upstream source snapshot vX.Y.Z"

# ⑥ 回到 main 做三方合并（后续与路径 A 的 ④⑤ 相同）
git checkout main
git merge --no-commit "sync/snapshot-$(date +%Y%m%d)"
# 解冲突 → 第 6 节验证 → git commit
```

> 排除项用数组共用，是为了让 dry-run 与真跑完全一致 —— 两条命令只差 `--dry-run`，不会出现「预览时排除了、真跑时漏写」的情况。`SRC_DIR` 必须是解压后的**仓库根目录**（里面有 `build.sh`、`Sources/`），不是外层那个包一层目录。

### 4.3 源码包特有的风险

| 风险 | 说明与处理 |
|---|---|
| 归档不含隐藏文件 | release 的 zip 通常不含 `.github/`、部分 dotfile。rsync 的 `--delete` 会把它们表现为「删除」，merge 后一并删掉。**必须**审阅 ⑤ 输出的删除列表（`git diff --name-status "$BASE" -- . \| /usr/bin/grep '^D'`），误删的用 `git checkout "$BASE" -- <path>` 找回后再 `git add -A` |
| 归档不是 `main` 而是旧 tag | 快照分支仍从定制基线 commit 切出（见定制改动记录.md 顶部），但要在 commit message 里写明 tag/版本号，避免以后误以为已同步到最新 |
| macOS 的 rsync 是 openrsync | `/usr/bin/rsync` 不是 GNU rsync，`--delete` 与 exclude 的边界行为略有差异。务必先 `--dry-run`，不要凭 GNU rsync 的经验直接跑 |
| 二进制资源 | `docs/demo.gif`（约 30 MB）、`docs/assets/`、图标资源上游都有；若归档缺了它们，`--delete` 会误删，同样按删除列表找回 |

## 5. 冲突处理手册

### 5.1 会冲突的 10 个文件（逐项策略）

上游只要动了同一区域就会冲突。解决时**不要整边接受**：先看上游改了什么，再把定制片段重新贴上去。

| # | 文件 | 本仓库的定制锚点 | 上游可能改动 | 解决原则 |
|---|---|---|---|---|
| 1 | `build.sh` | 官方变体 `else` 分支中的 `BUILD_VARIANT_FLAGS=(-D VORSSAINT_CUSTOM_BUILD)` | 变体逻辑、编译参数、签名流程重构 | **P0**：合并后必须仍有 `-D VORSSAINT_CUSTOM_BUILD`。丢了它，`isCustomBuild` 全为 false，自更新重新打开，一次更新就会把整个 fork 覆盖成官方版。上游若改了变体分支结构，把标志挪到新的官方构建分支里 |
| 2 | `Sources/Vorssaint/Core/Defaults.swift` | ① `DefaultsKey.panelShowBrandMark`；② `registeredDefaults` 开头的 `panelShowBrandMark: false`；③ `autoCheckUpdates: AppInfo.defaultAutoCheckUpdates` | 新增偏好 key、重排 `registeredDefaults` | 保留三项。注意 `SettingsBackupSupport.exportKeys()` 从 `registeredDefaults` 取键，我们的 key 丢了就退出设置备份。上游若把 `autoCheckUpdates` 默认值改成别的表达式，保留 `AppInfo.defaultAutoCheckUpdates` 语义（定制构建为 false） |

### 5.2 纯新增文件（不会冲突，但合并后要确认还在）

```
Sources/Vorssaint/Core/PanelBrandMarkStrings.swift
Sources/Vorssaint/Core/CustomBuildUpdateStrings.swift
Sources/Vorssaint/UI/Settings/CustomBuildUpdateNotice.swift
build-and-run.sh
docs/定制改动记录.md
docs/上游源码合并指南.md
```

- `build.sh` 用 zsh 递归 glob `APP_SOURCES=(Sources/Vorssaint/**/*.swift)` 收集主 App 源码，**新增 Swift 文件自动纳入编译，不需要登记**。
- 但 `TEST_SOURCES`（`build.sh` 中以 `TEST_SOURCES=(` 开头的那个数组）是**显式列表**，由上游维护。测试 target 不带 `VORSSAINT_CUSTOM_BUILD`，所以含定制逻辑或依赖定制编译标志的文件**不要**加进去。**例外**：`Sources/Vorssaint/Core/PanelBrandMarkStrings.swift` 自 2026-11-22 起**必须**登记（已在 build.sh 中），因为上游 `SettingsSearchCoverageTests` 要在测试 target 里解析 `PanelBrandMarkStrings.localized(...).title` —— 该文件是纯字符串结构体、没有条件编译，登记是安全的。其余两个定制文件（`CustomBuildUpdateStrings.swift`、`CustomBuildUpdateNotice.swift`）仍**不要**加。
- 上游新增的 Swift 文件同理自动纳入主 App；若上游同时改了 `TEST_SOURCES`，让上游那部分整体进来，不要手工删改。
- 上游新增本地化语言时不会与我们的独立 `Strings` 文件冲突 —— 这正是把定制文案放在独立文件、不碰 `Core/Localizations/Strings+*.swift` 的原因。

### 5.3 三条通用原则

1. 冲突文件先看 `git diff --ours` / `git diff --theirs` 再动手，尤其 `MenuPanelView.swift` 和 `build.sh`。
2. **编译标志是定制版的生命线**（第 5.1 节 #1）。任何合并之后第一件事都是确认它还在。
3. 上游若重构掉了某个锚点（例如删掉 `MenuPanelHeader`），不要硬把旧代码贴回去；按新结构重新实现同等语义，并在 `docs/定制改动记录.md` 追加一条说明。

## 7. 收尾：落库、推送、更新记录

1. 验证通过后提交合并结果（commit message **不加** `Co-Authored-By` 之类的署名行），再 `git checkout main && git merge --ff-only <集成分支>`。
2. `git push origin main` **只在老夏明确指示后执行**，默认不 push，更不 `--force`。
3. 更新 `docs/定制改动记录.md`：
   - 顶部「定制基线 commit」改为本次合并进来的**上游 HEAD**（`git rev-parse upstream/main`）。注意不是 fork `main` 的 merge commit —— 下一次合并的 merge base 是上游那个 commit。
   - 「三、合并上游时的注意点」按上游实际改动更新冲突文件清单。
   - 「五、验证记录」「六、修订记录」各追加一行。
4. 上游若改了 `Resources/Info.plist` 的版本号：随它更新即可。自更新已关闭，版本比对不再触发 DMG 覆盖；但 `What's New` / Release Notes 一类按版本匹配的逻辑会读到新值，顺手看一眼。
5. 合规：上游为 GPL-3.0，合并时保留 `LICENSE` 与源文件头部的 `SPDX-License-Identifier` / 版权声明；对外分发定制构建时遵守该许可证。

## 8. 回滚

| 场景 | 命令 |
|---|---|
| 合并停在工作区、还没提交 | `git merge --abort`（回到合并前状态） |
| 集成分支已提交但还没合进 `main` | `git checkout main && git branch -D sync/upstream-YYYYMMDD`，集成结果整体丢弃 |
| 已合进 `main`、还没 push | `git reset --hard fork-before-upstream-YYYYMMDD`（**先确认工作区没有要留的改动**，此命令会丢弃未提交内容） |
| 已经 push 到 `origin` | 用 `git revert -m 1 <merge-commit-sha>` 生成反向提交，**不要** `reset --hard` + 强推 |
| 合并前打的 tag 误删了别的 | `git show fork-before-upstream-YYYYMMDD --stat` 可核对锚点内容 |

## 9. 常见坑

| 坑 | 后果 / 处理 |
|---|---|
| 带着未提交的定制改动直接 merge | git 拒绝合并，或改动被卷进上游提交里难以拆分。第 1.2 节先处理 |
| 用 `git checkout upstream/main -- .` 或解压覆盖工作区 | 定制改动被整片抹掉，且没有三方合并可用。走路径 B 的快照分支法 |
| 接受了上游 `build.sh` 的「theirs」 | `-D VORSSAINT_CUSTOM_BUILD` 丢失 → 自更新复活 → 某次点击更新后 App 变回官方版。第 5.1 节 #1 |
| 上游新增了第二个安装入口 | `downloadAndInstall` 有短路但新入口没有。合并后全文搜 `install` / `DMG` / `replace` 相关调用点 |
| 上游改了面板行高常量 | 我们的 chrome 公式写死 `38 / 34 / 36 / 24 / 12`，不同步会出现空白或裁切。第 5.1 节 #5 |
| 把定制 Swift 文件加进 `TEST_SOURCES` | 测试 target 不带编译标志，可能让上游偏好契约测试失败。第 5.2 节 |
| `docs/demo.gif` / `docs/assets` 被源码包 `--delete` 误删 | 路径 B 的删除列表审阅，第 4.3 节 |
| `git fetch` 报 `Empty reply from server` | 走 `127.0.0.1:7897` 代理，第 2 节 |
| 合并后忘了更新基线 commit | 下次合并时 `docs/定制改动记录.md` 里的基线过时，冲突核对会找错参照点。第 7 节第 3 条 |
| 误提交 `.openidea/` / `.workbuddy/` | 用 `.git/info/exclude` 本地排除，不改仓库 `.gitignore`，第 1.2 节 |
